# GCGUI Web Server — Beginner-Friendly TODO

This is the working plan for rebuilding **GCGUI as a web application**.

The goal is to keep the useful parts of the existing GCGUI project, replace its Electron desktop-only backend with a Python server, and let other devices connect through Wi-Fi, a LAN, or a phone hotspot.

You do **not** need to understand every item before starting. Work from top to bottom. Each task explains what it means, why it exists, and what “done” looks like.

## 2. Get a tiny server running before doing complicated things

### [ ] 2.1 Make the first FastAPI app

Create `backend/app/main.py` with a tiny app that has a health-check URL.

A **health check** is a simple URL that says “the server is alive.” It lets us test the server before serial hardware is involved.

Example:

```python
from fastapi import FastAPI

app = FastAPI(title="GCGUI Web Server")


@app.get("/api/health")
async def health():
    return {"status": "ok"}
```

### [ ] 2.2 Start the server

From the project root:

```bash
uv run uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1 --port 8000
```

Open these addresses on the same computer:

- `http://127.0.0.1:8000/api/health` — should show `{"status":"ok"}`.
- `http://127.0.0.1:8000/docs` — interactive API documentation generated by FastAPI.

Stop the server with `Ctrl+C` in the terminal.

**Done when:** Both URLs load without an error.

> Keep `127.0.0.1` for initial development. Later, when you intentionally want other devices to connect, bind to `0.0.0.0` and configure the firewall. Do not expose serial-control endpoints to an untrusted network.

## 3. Rebuild the serial connection in Python

This is the first major hardware task. The original `electron/main.js` is the behavioral reference.

### [ ] 3.1 Understand what serial communication does

The server needs to:
1. List serial devices connected to the server computer.
2. Open exactly one selected device at the chosen baud rate.
3. Read incoming data continuously.
4. Send data when the user requests it.
5. Close the connection cleanly.
6. Report connection errors and status changes.

A **baud rate** is the communication speed setting. The original GCGUI defaults to `115200`, but the new version should let the user select a value.

### [ ] 3.2 Implement `hardware/serial_manager.py`

Create a `SerialManager` class. It should be the only part of the backend that directly opens the physical serial port.

Suggested responsibilities:

- `list_ports()` — return available port details.
- `connect(port, baud_rate)` — open the selected port.
- `disconnect()` — close it.
- `send(data)` — transmit data.
- A background reader — collect incoming lines and pass them to the data manager.
- Connection state — report whether the port is connected and any error.

**Important beginner warning:** Serial ports are usually exclusive. If the Arduino IDE's Serial Monitor or another program already has the port open, GCGUI may not be able to open it. Close other serial-monitor programs before testing.

### [ ] 3.3 Handle disconnects and reconnects safely

The old Electron code contains careful logic to avoid opening a port twice or trying to reconnect before the previous connection has fully closed.

Recreate the behavior, not the Electron-specific implementation.

Test these cases:

- [ ] Connect to a real device.
- [ ] Disconnect normally.
- [ ] Unplug the USB cable while connected.
- [ ] Try connecting to a port that is already in use.
- [ ] Select a different port.
- [ ] Change the baud rate and reconnect.
- [ ] Click connect twice quickly.
- [ ] Shut down the server while connected.

**Done when:** The server does not leave a port stuck open and reports errors clearly.

### [ ] 3.4 Add serial API routes

Implement the serial routes in `api/routes/serial.py`.

Initial API design:

| Method | URL | Purpose |
|---|---|---|
| `GET` | `/api/serial/ports` | List available serial ports. |
| `GET` | `/api/serial/status` | Get current connection status. |
| `POST` | `/api/serial/connect` | Connect to a selected port. |
| `POST` | `/api/serial/disconnect` | Disconnect. |
| `POST` | `/api/serial/send` | Send data to the device. |

The request body for connect should contain a port name and baud rate. Validate it rather than accepting arbitrary input.

**Done when:** You can test these operations using `http://127.0.0.1:8000/docs`, without the React interface.

## 4. Establish one consistent data path

### [ ] 4.1 Create `services/data_manager.py`

This module receives incoming serial lines and decides what should happen to them.

For the first version, keep it simple:

1. Receive a line from the serial manager.
2. Preserve the raw line.
3. Send it to the recording manager if recording is active.
4. Send it to connected browser clients.
5. Later, add parsing and structured data events.

Do not make every widget read from the serial port directly. The serial manager should have one reader, and the data manager should distribute the result.

### [ ] 4.2 Define message formats

Choose a consistent JSON message shape for WebSocket communication. For example:

```json
{
  "type": "serial_data",
  "timestamp": "2026-01-01T12:00:00Z",
  "data": "2172.562 R29 0000052C 00 00 FF FF FF FF FF FF"
}
```

This is an example of the new network message envelope, not a replacement for the original CRTD line format.

Also define status messages, such as:

```json
{
  "type": "serial_status",
  "connected": true,
  "port": "/dev/ttyUSB0",
  "baud_rate": 115200
}
```

Write down the message shapes in one place and keep them stable. The React frontend and Python backend both depend on them.

### [ ] 4.3 Implement `services/broadcast_manager.py`

This module keeps track of connected WebSocket clients and sends them updates.

It should:

- Add a client when it connects.
- Remove a client when it disconnects.
- Broadcast serial data and status updates.
- Handle a client that disconnects unexpectedly.
- Avoid letting one slow browser block serial reading or recording.

For the first version, an in-memory list of connected clients is acceptable because the app will run as one server process. More advanced multi-server broadcasting is not needed yet.

### [ ] 4.4 Implement `api/websocket.py`

Create `/ws` as the WebSocket endpoint.

The browser should receive:
- Serial data.
- Serial connection status.
- Recording status.
- Replay status.
- Later, parsed CAN/CSV data.

The browser may also send commands over the socket, but use HTTP POST routes for important actions at first. Keep the protocol easy to debug.

**Done when:** A simple browser or test script can connect to `/ws` and receive a test message.

## 5. Preserve the existing React frontend

### [ ] 5.1 Bring over the existing frontend

The existing GCGUI uses React and Vite. The new application can still use React and Vite; Electron is not required for those.

Copy the relevant frontend source from the original project into the new `frontend/` directory. Do this carefully rather than copying the old Electron folder into the frontend.

Likely candidates to preserve:

- `src/components/` — dashboard widgets and UI components.
- `src/components/parsers/` — existing CAN and CSV processing components.
- `src/utils/` — math, formatting, parsing, and helper functions.
- `src/App.css` and `src/index.css` — styling.
- `src/assets/examples/` — example dashboard configurations and example data.

Do not blindly copy files that only exist to support Electron. Check imports after copying.

### [ ] 5.2 Keep the widgets whenever possible

The existing widgets are mostly frontend code. They should not need to know how the serial cable works.

Review and preserve these components where possible:

- `NumberWidget.jsx`
- `BitfieldWidget.jsx`
- `DischargeCalcWidget.jsx`
- `LinePlotWidget.jsx`
- `FullHistoryGraph.jsx`
- `RawSerialWidget.jsx`
- `BrowserWidget.jsx`
- `RadioWidget.jsx`
- `SendWidget.jsx`
- `KeySendWidget.jsx`
- `KeyButtonWidget.jsx`
- `Palette.jsx`
- `Editor.jsx`
- `ControlBar.jsx` (may need changes because it controls serial/recording/replay)

The goal is to change where the data comes from, not redesign every widget.

### [ ] 5.3 Replace `window.electronAPI`

The original `electron/preload.js` creates `window.electronAPI` and provides functions such as:

- `getSerialPorts`
- `connectSerialPort`
- `disconnectSerialPort`
- `startLiveRecording`
- `stopLiveRecording`
- `onSerialData`
- `onSerialConnectionStatus`
- `loadCRTDFile`
- `startReplay`
- `pauseReplay`
- `stopReplay`
- `getReplayStatus`
- `seekReplay`
- `injectSerialData`
- `sendSerialData`
- `onReplayStatus`

That bridge will not exist in a normal browser.

Create frontend service files instead:

```text
frontend/src/services/
    api.ts
    websocket.ts
```

- `api.ts` makes HTTP requests to FastAPI.
- `websocket.ts` connects to `/ws` and distributes incoming messages to React.

Then update components that call `window.electronAPI` to use these services or React hooks that wrap them.

**Done when:** The frontend no longer requires `window.electronAPI` to load and can show server connection status.

## 6. Decide where parsing happens

The old project already has useful JavaScript parsing code. Do not rewrite it just because the backend is changing languages.

### [ ] 6.1 Start by preserving the JavaScript parsers

Initial recommendation: let Python read the serial lines and broadcast them; let the existing React/JavaScript parsing code interpret them.

Relevant existing files include:

- `src/components/parsers/canproc.jsx`
- `src/components/parsers/csvproc.jsx`
- `src/utils/crtdParser.js`
- `src/utils/csvLogParser.js`
- `src/utils/csvAliases.js`

This is the lower-risk path because it avoids changing parser behavior and frontend expectations all at once.

### [ ] 6.2 Add Python parsers only if there is a reason

If you later need parsing to happen once on the server and be shared identically by every browser, port the parser logic to:

- `backend/app/parsers/can_parser.py`
- `backend/app/parsers/csv_parser.py`
- `backend/app/parsers/crtd_parser.py`

Do not maintain two competing parser implementations indefinitely. If you port one, add tests comparing its output against known examples from the old project.

### [ ] 6.3 Test both supported data formats

The original README documents two serial data modes:

**CRTD / CAN-like text lines:**

```text
2172.562 R29 0000052C 00 00 FF FF FF FF FF FF
```

**CSV lines:**

```csv
timestamp,datapt1,datapt2
0.00,-11.73,-10.20
0.11,-11.73,-11.73
```

Test real example files and known-good samples. Do not assume every serial device sends exactly the same format.

## 7. Recording: save data on the server

### [ ] 7.1 Implement `services/recording_manager.py`

The original GCGUI records incoming serial lines to files in the user's Documents folder under `gcgui-recordings`.

The original recording code:
- Uses `.csv` for CSV recordings.
- Uses `.crtd` for CAN/CRTD recordings.
- Adds a comment/header line identifying the live capture and its time.
- Writes incoming lines to the active recording.
- Stops and closes the file when recording ends or the protocol changes.

The new server should save recordings under:

```text
data/recordings/
```

The browser should ask the server to start or stop recording. The server should perform the actual file writing.

### [ ] 7.2 Preserve compatibility with old recordings

Do not casually change:
- File extensions.
- Header lines.
- Timestamp representation.
- Line contents.
- Line ordering.

The old replay code may depend on these details.

### [ ] 7.3 Add recording routes

Suggested routes:

| Method | URL | Purpose |
|---|---|---|
| `POST` | `/api/recording/start` | Start recording in `can` or `csv` mode. |
| `POST` | `/api/recording/stop` | Stop the active recording. |
| `GET` | `/api/recording/status` | Report whether recording is active and the file name. |
| `GET` | `/api/recording/list` | List recordings available to the user. |

**Done when:** You can record a short session, stop it, and open the output file to verify its contents.

## 8. Replay: play saved recordings

### [ ] 8.1 Understand replay

Replay means the server reads a saved recording line by line and emits the lines at approximately the same timing as the original data.

The original Electron bridge supports:
- Load a CRTD file.
- Start replay at a selected speed.
- Pause replay.
- Stop replay.
- Get replay status.
- Seek to a selected index.

The new app should preserve these capabilities.

### [ ] 8.2 Implement `parsers/crtd_parser.py` and `services/replay_manager.py`

First inspect the original `src/utils/crtdParser.js` and the replay logic in `electron/main.js`.

Preserve the original file interpretation. The new replay manager should:
- Load a selected recording.
- Track the current position.
- Play at a chosen speed.
- Pause and resume.
- Stop and reset.
- Seek to a position.
- Broadcast replay status and replayed data to browsers.

### [ ] 8.3 Add replay API routes

Suggested routes:

| Method | URL | Purpose |
|---|---|---|
| `POST` | `/api/replay/load` | Load a recording already stored on the server. |
| `POST` | `/api/replay/start` | Start or resume replay. |
| `POST` | `/api/replay/pause` | Pause. |
| `POST` | `/api/replay/stop` | Stop. |
| `GET` | `/api/replay/status` | Get current replay state. |
| `POST` | `/api/replay/seek` | Move to a selected position. |

**Security note:** Do not let a browser submit an arbitrary filesystem path and make the server open it. The server should accept a recording ID or a file selected from its own recordings directory.

**Done when:** A saved recording can be replayed and the existing widgets update as if the data were arriving live.

The original project has example JSON dashboard configurations under `src/assets/examples/`.

The first goal is to keep old dashboard JSON files loading in the new frontend.

### [ ] 9.2 Decide where configurations live

For the first version, save server-managed configurations under:

```text
data/configurations/
```

Possible routes:

| Method | URL | Purpose |
|---|---|---|
| `GET` | `/api/config` | List or load configurations. |
| `POST` | `/api/config` | Save a configuration. |
| `DELETE` | `/api/config/{id}` | Delete a configuration. |

Validate configuration JSON before saving it. Do not allow a submitted file name to write outside the configuration directory.

**Done when:** An existing example layout can be loaded, edited, saved, and loaded again.

## 10. Connect everything and test multiple browsers

### [ ] 10.1 Make a complete local test

Before trying Wi-Fi, make sure the app works on the same computer.

Test this sequence:

1. Start the Python server.
2. Open the frontend.
3. Connect a serial device.
4. Confirm that raw serial data appears.
5. Start a recording.
6. Stop the recording.
7. Load the recording.
8. Replay it.
9. Confirm the widgets update.

### [ ] 10.2 Test more than one browser

Open the same web application in two browser windows.

- [ ] Both can see the same serial data.
- [ ] Disconnecting one browser does not stop the server.
- [ ] Disconnecting one browser does not stop recording.
- [ ] A slow or closed browser does not block the other browser.
- [ ] The server still has only one physical serial connection.

Decide whether all users can control the hardware or whether only an administrator can connect/disconnect/send. This matters before using it on a shared network.

## 11. Make it accessible over Wi-Fi / hotspot

### [ ] 11.1 Bind the server to the network

For local-only development, use `127.0.0.1`.

When you are ready for another device to connect, run:

```bash
uv run uvicorn app.main:app --app-dir backend --host 0.0.0.0 --port 8000
```

`0.0.0.0` means the server listens on available network interfaces. It does **not** mean that the website is automatically public on the internet.

### [ ] 11.2 Find the server computer's local IP address

On Linux:

```bash
hostname -I
```

Use the relevant Wi-Fi or hotspot address, then open this from the other device:

```text
http://SERVER-IP:8000
```

For example, if the server computer's address is `192.168.1.25`, open `http://192.168.1.25:8000`.

### [ ] 11.3 Configure the firewall

Allow incoming connections to TCP port `8000` only on the network you intend to use. The exact command depends on your Linux firewall (for example, firewalld or ufw).

Do not turn off the firewall entirely just to make the app work.

### [ ] 11.4 Add access control before sharing

This application can send commands to physical hardware. Before letting other people connect:

- Add authentication or a simple access code.
- Restrict who can connect/disconnect the serial device.
- Restrict who can send serial data.
- Validate all commands and file names.
- Avoid exposing the server directly to the public internet.
- Consider read-only access for viewers.

**Done when:** A phone connected to the same Wi-Fi or hotspot can open the app, view data, and only perform actions it is authorized to perform.

## 12. Quality checks and finish work

### [ ] 12.1 Add tests

Start with tests for the parts that can be tested without hardware:

- Parser tests using sample CRTD and CSV lines.
- Recording format tests.
- Replay timing/state tests.
- API tests for invalid requests.
- WebSocket connection/disconnection tests.
- Configuration validation tests.

Use a fake serial device or mocked serial manager for most automated tests. You should not need to plug in hardware every time you run the test suite.

### [ ] 12.2 Add logging and useful errors

The server should explain problems in plain language:
- Serial port not found.
- Port already in use.
- Device disconnected.
- Invalid baud rate.
- Unsupported recording format.
- Recording could not be written.
- Replay file not found.
- Browser disconnected.

Avoid silently swallowing errors.

### [ ] 12.3 Make startup simple

Eventually, provide one documented command to start the backend and one documented command to start the frontend in development.

Do not worry about a one-click installer until the app itself works.

## 13. Suggested first milestone

Do **not** try to complete all sections at once.

The first milestone is deliberately small:

- [ ] FastAPI server starts.
- [ ] `/api/health` works.
- [ ] Server lists serial ports.
- [ ] Server connects to one serial device.
- [ ] Server reads incoming lines.
- [ ] One browser connects to `/ws`.
- [ ] Browser displays incoming raw serial lines.

Once that works, you have proven the most important new idea: **Python can read the hardware and send its data to a web browser over the network.**

Then add recording, replay, parsers, and the full dashboard.
